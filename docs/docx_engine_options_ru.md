# DOCX engine: варианты доведения до профессионального уровня

Текущий hotfix возвращает DOCX на стабильный rich-reader, чтобы убрать пустой экран. Это не финальная архитектура. Для профессионального DOCX-viewer нужно выбрать тяжёлый путь.

## Вариант 1 — собственный OOXML page-layout engine

Плюсы:
- полный контроль внутри ReadArc;
- работает оффлайн;
- без серверных зависимостей;
- единая логика на Android/macOS/iOS/desktop.

Минусы:
- самый длинный путь;
- нужно реализовать полноценную модель Word layout: styles, numbering, tables, sections, headers/footers, page breaks, поля, табы, floating objects.

Подходит как стратегический путь, но его надо делать отдельным большим спринтом с тестовыми DOCX-наборами.

## Вариант 2 — DOCX → HTML/CSS → WebView

Плюсы:
- быстрее получить хороший визуальный результат;
- WebView хорошо решает текст, таблицы, изображения, CSS;
- проще сделать одинаковый fit-to-width на Android/macOS/iOS.

Минусы:
- нужен надёжный embedded конвертер DOCX → HTML/CSS;
- надо писать/встраивать слой преобразования OOXML styles/numbering/tables/images;
- выделение/копирование и синхронизацию позиции нужно аккуратно связать с HTML anchors.

Практичный ближайший вариант: сделать локальный processed artifact `book.docx.readarc.html` и открывать его во встроенном WebView/HTML-renderer.

## Вариант 3 — DOCX → PDF artifact → существующий PDF reader

Плюсы:
- почти идеальная фиксированная страница;
- можно переиспользовать уже хороший PDF/DJVU page-reader;
- на мобильном лист масштабируется без reflow.

Минусы:
- нужен конвертер DOCX → PDF;
- если конвертер серверный, появляется server-side processing;
- если конвертер нативный внутри клиента, нужны тяжёлые зависимости.

Это сильный вариант для production, если принять pipeline processed artifacts: оригинал хранится всегда, рядом создаётся подготовленное представление.

## Вариант 4 — platform-native preview

Плюсы:
- на macOS/iOS можно приблизиться к системному качеству через QuickLook/WebKit-пути;
- быстро для Apple-платформ.

Минусы:
- нет единой реализации на Android/Windows/Linux;
- сложнее синхронизировать выделение, anchors и одинаковый UX;
- может нарушить цель одинакового встроенного reader-а.

Подходит только как временный платформенный fallback, не как единая архитектура ReadArc.

## Рекомендация

Для ReadArc лучше идти в два слоя:

1. Краткосрочно: DOCX → HTML/CSS artifact + WebView/HTML renderer, чтобы быстро получить профессиональную читаемость, таблицы, изображения и стабильный мобильный fit-to-width.
2. Долгосрочно: собственный page model поверх OOXML/HTML artifacts, если понадобится полный контроль над Word-layout.

DOCX → PDF тоже стоит держать как вариант для документов, где критична именно печатная постраничная верстка.
